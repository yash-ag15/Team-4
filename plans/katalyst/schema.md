# Database schema — Katalyst

**Owner: Siddesh.** He is the only person who runs `npm run db:migrate`. Everyone else
reads this file and the code in `src/db/schema/`.

Files, one per concern, so two people adding a table edit two different files:

| File | Tables |
|---|---|
| `src/db/schema/auth.ts` | `user`, `session`, `account`, `verification` — **GENERATED**, never hand-edit |
| `src/db/schema/courses.ts` | `courses`, `course_sections`, `lessons`, `assessments` |
| `src/db/schema/learning.ts` | `enrollments`, `lesson_progress`, `section_progress`, `submissions`, `ai_reviews` |
| `src/db/schema/engagement.ts` | `xp_events`, `streaks`, `daily_checkins`, `badges`, `user_badges`, `challenges`, `challenge_progress` |
| `src/db/schema/social.ts` | `notifications`, `teams`, `team_members` — good-to-have, ship last |

`src/db/schema/index.ts` is **append-only**: one `export * from './<file>'` line per file.

### Two conventions that are not negotiable

1. **`text` ids, not `uuid`.** Real inserts get a UUID from `$defaultFn`, but a text id also
   lets the seed write the fixtures' literal ids (`course-1`, `sec-1`, …) so seeded rows
   carry the **same ids the contract mocks serve**. That is what makes flipping a route
   from mock to live a non-event: `/learn/data-foundations` resolves in both modes. It also
   matches Better Auth's text `user.id`.
2. **XP is `integer`.** Never a numeric, never a float. Percentages are `0-100` integers.

## 1. `user` — generated by Better Auth

Do not edit `src/db/schema/auth.ts`. Edit `additionalFields` in `src/lib/auth.ts` and run
`npm run auth:generate`.

```ts
// src/lib/auth.ts — the Katalyst profile
export const SYSTEM_ROLES = ['student', 'mentor', 'admin'] as const

additionalFields: {
  // authorization — server-owned. input:false is load-bearing (see AGENTS.md rule 6).
  systemRole:         { type: [...SYSTEM_ROLES], required: false, defaultValue: 'student', input: false },

  // Katalyst profile — all optional, or Google sign-up breaks (AGENTS.md rule 5)
  cohortYear:         { type: 'string',  required: false, defaultValue: '' },   // '2026'
  campus:             { type: 'string',  required: false, defaultValue: '' },
  phone:              { type: 'string',  required: false, defaultValue: '' },
  city:               { type: 'string',  required: false, defaultValue: '' },

  // the onboarding gate — server-owned so it cannot be faked
  onboardingComplete: { type: 'boolean', required: false, defaultValue: false, input: false },
}
```

**Becoming a mentor.** `systemRole` can never come from a request body. Two legitimate
paths, both server-side:

- Admin promotes: `POST /api/admin/users/:id/role` (`auth: 'admin'`).
- Onboarding with a code: the client may send `mentorCode`; `src/server/users.ts` compares
  it to `process.env.MENTOR_SIGNUP_CODE` and only then writes `systemRole: 'mentor'`. The
  code is never sent to the client and the field is never echoed back.

## 2. Courses

### `courses`

| Column | Type | Notes |
|---|---|---|
| `id` | text PK | `course-1`, … |
| `slug` | text unique | URL: `/learn/data-foundations` |
| `title` | text | |
| `subtitle` | text default `''` | one line for the catalog card |
| `description` | text default `''` | |
| `coverEmoji` | text default `'📘'` | cheap visual identity, zero asset pipeline |
| `category` | enum | `technical` `business` `communication` `leadership` `wellbeing` |
| `track` | enum | **`mandatory`** or **`optional`** |
| `difficulty` | enum | `beginner` `intermediate` `advanced` |
| `certificateEligible` | boolean default false | completing awards `CERTIFICATE_BONUS` + a badge |
| `estimatedHours` | integer default 0 | |
| `xpBonusOnComplete` | integer default 100 | on top of section XP |
| `dueAt` | timestamptz null | mandatory courses are time-based; null for optional |
| `status` | enum | `draft` `published` `archived` — only `published` shows in the catalog |
| `mentorId` | text → `user.id` | the owning mentor; drives the review queue and roster |
| `createdAt` / `updatedAt` | timestamptz | |

**Mandatory vs optional is the core motivation lever.** Mandatory courses carry a `dueAt`
and appear in "due soon". Optional courses carry **no** deadline and earn
`OPTIONAL_TRACK_MULTIPLIER = 1.5` on every course-derived XP award. The catalog card shows
either a due-date chip or a **`1.5x XP`** chip — never both.

### `course_sections`

`id` · `courseId` → courses (cascade) · `title` · `summary` default `''` ·
`orderIndex` integer · `xpAward` integer default 50 · `createdAt`

A section is the unit of XP. Completing every lesson in it fires one award.

### `lessons`

`id` · `sectionId` → course_sections (cascade) · `title` · `kind` enum
(`video` `reading` `link`) · `contentUrl` text default `''` · `contentBody` text default
`''` · `durationMin` integer default 5 · `orderIndex` integer · `xpAward` integer default
10 · `createdAt`

`contentBody` holds markdown for `reading`; `contentUrl` holds the URL for `video`/`link`.
No file uploads in six hours.

### `assessments`

| Column | Type | Notes |
|---|---|---|
| `id` | text PK | |
| `courseId` | text → courses (cascade) | |
| `sectionId` | text → course_sections, **nullable** | null = course-level final |
| `title` | text | |
| `prompt` | text | what the student must do — goes into the AI Coach prompt |
| `rubric` | text | how it is judged — **this is what makes the AI review specific** |
| `kind` | enum | `assignment` `quiz` `project` `reflection` |
| `maxScore` | integer default 100 | |
| `xpAward` | integer default 150 | the **ceiling** on the mentor's `finalXp` |
| `dueAt` | timestamptz null | |
| `orderIndex` | integer | |
| `createdAt` | timestamptz | |

A weak `rubric` produces a vague AI review. Every seeded assessment gets a real 3-5
criterion rubric. This is Riya's highest-leverage 20 minutes.

## 3. Learning

### `enrollments`

`id` · `courseId` → courses · `studentId` → user · `status` enum
(`active` `completed` `dropped`) · `enrolledAt` · `completedAt` null · `progressPct`
integer default 0 · `xpEarned` integer default 0

**`unique(courseId, studentId)`** — a student enrols once. Enrolling twice is a `CONFLICT`,
not a second row.

`progressPct` and `xpEarned` are denormalised for fast list rendering. The ledger
(`xp_events`) is the source of truth; these are a cache recomputed on every progress write.

### `lesson_progress`

`id` · `enrollmentId` → enrollments (cascade) · `lessonId` → lessons (cascade) ·
`completedAt` — **`unique(enrollmentId, lessonId)`**

### `section_progress`

`id` · `enrollmentId` → enrollments (cascade) · `sectionId` → course_sections (cascade) ·
`completedAt` · `xpAwarded` integer — **`unique(enrollmentId, sectionId)`**

Exists purely so a section award happens exactly once, even if the last lesson is marked
complete twice by a double-clicked button.

### `submissions`

| Column | Type | Notes |
|---|---|---|
| `id` | text PK | |
| `assessmentId` | text → assessments | |
| `studentId` | text → user | |
| `enrollmentId` | text → enrollments | |
| `content` | text | the student's answer |
| `attachmentUrl` | text default `''` | a link, not an upload |
| `status` | enum | `draft` `submitted` `ai_reviewed` `mentor_approved` `changes_requested` |
| `aiScore` | integer null | **denormalised from `ai_reviews`, for list views** |
| `aiXpSuggested` | integer null | ditto |
| `finalScore` | integer null | the mentor's number |
| `finalXp` | integer null | the mentor's number — capped at `assessment.xpAward` |
| `mentorId` | text → user, null | who decided |
| `mentorNote` | text default `''` | |
| `reviewedAt` | timestamptz null | |
| `submittedAt` / `updatedAt` | timestamptz | |

The status ladder is the whole workflow:
`submitted` → (AI Coach runs) → `ai_reviewed` → (mentor decides) →
`mentor_approved` **or** `changes_requested`.

Only the `mentor_approved` transition writes an `xp_event`.

### `ai_reviews` — the USP artifact

| Column | Type | Notes |
|---|---|---|
| `id` | text PK | |
| `submissionId` | text → submissions (cascade) | |
| `model` | text | `gemini-2.5-flash` — recorded so we can show it in the demo |
| `summary` | text | 2-3 sentences the student reads first |
| `strengths` | jsonb `string[]` | |
| `weaknesses` | jsonb `string[]` | |
| `actionItems` | jsonb `string[]` | concrete "do this next" |
| `rubricBreakdown` | jsonb | `[{ criterion, score, maxScore, comment }]` |
| `suggestedScore` | integer | out of `assessment.maxScore` |
| `suggestedXp` | integer | **advice only** |
| `confidence` | enum | `low` `medium` `high` |
| `isPreview` | boolean default false | a `preview` run against a draft is not the real review |
| `latencyMs` / `tokensIn` / `tokensOut` | integer | for the "it really called Claude" slide |
| `createdAt` | timestamptz | |

**This table is written by `src/server/ai-coach.ts` and nothing else. It has no path to
`xp_events`.** That separation is the product's whole claim: the AI advises, the mentor
decides.

## 4. Engagement

### `xp_events` — the ledger, single source of truth

| Column | Type | Notes |
|---|---|---|
| `id` | text PK | |
| `userId` | text → user (cascade) | |
| `amount` | integer | always positive except `manual_adjust` |
| `reason` | enum | `lesson_complete` `section_complete` `course_complete` `certificate` `assessment_award` `daily_checkin` `streak_bonus` `challenge_complete` `badge_award` `manual_adjust` |
| `sourceType` | text | `lesson` `section` `course` `submission` `checkin` `streak` `challenge` `badge` `manual` |
| `sourceId` | text | the id within that type |
| `courseId` | text → courses, null | so per-course XP is one `where` |
| `awardedBy` | text → user, null | the mentor, for `assessment_award` |
| `note` | text default `''` | |
| `idempotencyKey` | text **unique not null** | see the table in `AGENTS.md` §10 |
| `createdAt` | timestamptz | drives yearly XP and month leaderboards |

**Every insert is `onConflictDoNothing({ target: idempotencyKey })`.** That single line is
what makes a double-clicked "Mark complete" harmless. Totals are always
`sum(amount) where userId = ?` — never a counter column that can drift.

Yearly XP is `sum(amount) where userId = ? and createdAt >= <Jan 1 of this year>`.

### `streaks`

`userId` text PK → user · `current` integer default 0 · `longest` integer default 0 ·
`lastCheckinDate` date null · `freezesLeft` integer default 2

### `daily_checkins`

`id` · `userId` → user · `checkinDate` date · `streakAfter` integer · `xpAwarded` integer ·
`createdAt` — **`unique(userId, checkinDate)`**

Check-in is deliberately the cheapest possible action worth 10 XP. It exists to make a
student open the app on a day they were not going to. That is the 80%-monthly-engagement
metric.

### `badges`

`id` text PK (slug: `first-submission`) · `name` · `description` · `emoji` ·
`criteria` text (human-readable) · `xpReward` integer default 25 · `rarity` enum
(`common` `rare` `epic` `legendary`) · `sortIndex` integer

Seeded, not authored. Ship with ~12: `first-steps`, `first-submission`, `week-warrior`
(7-day streak), `fortnight` (14), `section-sweeper`, `course-complete`, `certified`,
`self-driven` (3 optional courses), `top-ten`, `perfect-score`, `early-bird`, `comeback`.

### `user_badges`

`id` · `userId` → user · `badgeId` → badges · `earnedAt` — **`unique(userId, badgeId)`**

### `challenges`

`id` · `courseId` → courses **nullable** (null = global) · `title` · `description` ·
`kind` enum (`course` `weekly` `global`) · `targetType` enum (`lessons_completed`
`xp_earned` `submissions` `checkin_streak`) · `targetValue` integer · `xpReward` integer ·
`startsAt` · `endsAt` · `active` boolean default true

### `challenge_progress`

`id` · `challengeId` → challenges (cascade) · `userId` → user (cascade) · `current`
integer default 0 · `completedAt` timestamptz null — **`unique(challengeId, userId)`**

Progress is recomputed from `xp_events` and `lesson_progress` on read, not incremented on
write. Slower, but it cannot drift, and at hackathon data volumes it is free.

## 5. Social — good-to-have, ship last

### `notifications`

`id` · `userId` → user (cascade) · `kind` enum (`due_soon` `overdue` `xp_awarded`
`review_ready` `challenge` `nudge` `escalation`) · `title` · `body` · `href` text ·
`readAt` timestamptz null · `createdAt`

Generated on read (a "compute my notifications" query), not by a cron — Vercel Functions
scale to zero and we have no worker.

### `teams` / `team_members`

`teams`: `id` · `name` · `cohortYear` · `createdAt`
`team_members`: `id` · `teamId` → teams · `userId` → user — `unique(teamId, userId)`

Team XP is `sum(xp_events.amount)` joined through `team_members`. No separate ledger.

```sql
xp_events (user_id, created_at desc)      -- ledger + yearly XP + leaderboard

submissions (student_id)                  -- "my submissions"
courses (status, track)                   -- the catalog query
```

## 7. Seed plan — what "real" looks like

`npm run db:seed` is idempotent (`onConflictDoUpdate` on the fixture's own id) and reads
`src/mocks/factories.ts`, the **same** fixtures the contract mocks serve. Re-run it freely.

| Entity | Count | Shape |
|---|---|---|
| Users | 3 students, 2 mentors, 1 admin | `student1@katalyst.test` / `mentor@katalyst.test` / `admin@katalyst.test`, password `katalyst123` |
| Courses | 6 | 3 mandatory (with due dates), 3 optional, 1 of them certificate-eligible |
| Sections | ~20 | 3-4 per course |
| Lessons | ~50 | 2-4 per section |
| Assessments | 6 | one per course, each with a real 4-criterion rubric |
| Enrollments | 9 | each student on 3 courses, at different progress levels |
| Lesson progress | ~90 | so progress bars are at 20% / 55% / 90%, not all 0% |
| XP events | ~120 | spread over the last 60 days so yearly XP and the month leaderboard are non-trivial |
| Submissions | 4 | 1 draft, 1 `ai_reviewed` waiting in the queue, 2 `mentor_approved` |
| Badges | 12 | seeded definitions; ~6 already earned across the students |
| Challenges | 4 | 2 active global, 2 course-scoped |

**Nothing from the starter's NGO fixtures (`mockProjects`, `mockTasks`, the NGO
`mockUsers`) is ever seeded.** Those files are deleted in the first ten minutes.
