# AGENTS.md — Katalyst Gamified Learning Platform

**Read this file first, every session. It is the shared context for all 7 people and for
every Claude session in this repo.**

Stack: Next.js 16 (App Router) · Better Auth · Drizzle · Neon Postgres · Tailwind v4 ·
Anthropic SDK (`claude-opus-5`). One repo, 7 people, **6 hours**. The rules below exist so
the work merges cleanly and integrates on the first try.

---

## 1. What we are building

A gamified learning platform for Katalyst students. Students earn **XP** for meaningful
activity, mentors run courses and make the final call on scoring, and an **AI Coach**
reviews every submission.

**The USP — memorise this, it is the demo:**

> A student submits work → the **AI Coach reviews it**, names their **strengths and
> weaknesses**, tells them **what score and how much XP to expect** → the **mentor makes
> the final XP call**. The AI advises. The mentor decides.

That single sentence is why this project wins. Everything else is supporting cast.

**Hard invariant that encodes it:** the AI Coach **never** writes to `xp_events`. It writes
to `ai_reviews` only. XP is written by the XP engine (`src/server/xp.ts`) on system events
and on a **mentor decision**. If you find code where an AI response awards XP, that is a
bug — delete it.

### Success metrics we are demoing against

+25% active participation · +20% activity completion · 80%+ monthly engagement.
Every gamification feature must be traceable to one of those.

## 4. Hard rules

1. **Never create an API route without a contract.** Every endpoint is a `defineContract`
   in `src/contracts/<feature>.ts`, registered in `src/contracts/index.ts`. Route files are
   two lines and contain no logic.
2. **Never write `fetch('/api/...')` in a component.** Use `api.<feature>.<op>()` from
   `@/lib/api-client`. Typed, validated, and it can't drift from the server.
3. **Never run `drizzle-kit push`.** Shared Neon database — `push` silently drops other
   people's columns. Use `db:generate` + `db:migrate`, and **only Siddesh migrates**.
4. **Never hand-edit `src/db/schema/auth.ts`.** Generated by `npm run auth:generate` from
   `additionalFields` in `src/lib/auth.ts`. Edit the config, regenerate.
5. **Never make a Better Auth `additionalFields` entry `required: true`.** Google sign-in
   cannot supply custom fields, so a required field breaks Google sign-up. Optional +
   `defaultValue`, collected in `/onboarding`.
6. **Never set `input: true` on an authorization field.** `systemRole` is `input: false`.
   Anything `input: true` can be set by anyone POSTing to the sign-up endpoint.
7. **Never import `@/lib/auth` as a value in a client component.** Type-only import, or the
   DB driver ends up in the browser bundle.
8. **Never install another UI or data-fetching library.** shadcn components live in
   `src/components/ui`. The API client is `src/lib/api-client`.
9. **Never upgrade `drizzle-orm`.** Pinned to `0.45.2`; `@better-auth/drizzle-adapter`
   peers `^0.45.2`. The Drizzle docs' `@rc` instruction installs the v1 beta and breaks it.
10. **Never restructure `src/contracts/index.ts` or `src/db/schema/index.ts`.** Append one
    line. Seven people edit these files.
11. **Never write XP anywhere except `src/server/xp.ts`.** Every award goes through
    `awardXp()` with an `idempotencyKey`. A direct `db.insert(xpEvents)` outside that file
    is a bug — it is how a student gets double XP on a page refresh.
12. **Never call the Anthropic SDK outside `src/server/ai-coach.ts`.** One file owns the
    model, the prompt, the schema, the timeout and the fallback.
13. **Never edit a file outside your ownership column (§8) without pinging the owner.**
    Six hours does not survive a merge conflict in `globals.css`.

## 5. Conventions

- **Response envelope** — every route returns `{ ok: true, data, source }` or
  `{ ok: false, error: { code, message, fields? } }`. Set by `defineRoute`; don't hand-roll
  a `Response.json`.
- **Errors** — handlers `throw new ApiError('NOT_FOUND', 'Course not found')`. Codes:
  `VALIDATION_ERROR` `UNAUTHORIZED` `FORBIDDEN` `NOT_FOUND` `CONFLICT` `RATE_LIMITED`
  `INTERNAL`.
- **Dates cross the wire as ISO strings**, never `Date`. Contracts use `z.string()`.
- **GET inputs come from the query string** — use `z.coerce.number()` for numbers, never
  bare `z.number()`.
- **For query-string booleans use `z.stringbool()`, NEVER `z.coerce.boolean()`.**
  `z.coerce.boolean().parse('false') === true`, so `?done=false` would silently filter to
  done-only. `z.boolean()` is still correct for a real boolean in a JSON body.
- **`params` is a Promise** in Next 16. `defineRoute` awaits it for you.
- **Business logic lives in `src/server/<feature>.ts`**, never in a route file.
- **Auth in server components**: `await auth.api.getSession({ headers: await headers() })`.
  Middleware only does an optimistic cookie check — it is not the authorization boundary.
- **Node runtime everywhere.** Never `export const runtime = 'edge'`.
- **Integers only.** XP is `integer`, never a float. Percentages are `0-100` integers.

## 6. The contract folder — how a feature gets built

`src/contracts/` is **the** interface between frontend and backend. It is the only place
where the two halves agree on anything. Nothing else is a contract: not a Slack message,
not a comment, not a Figma frame.

Each feature also has a **plan folder** at `plans/katalyst/features/<id>-<name>/` holding
three files that must stay in sync with the contract:

```
plans/katalyst/features/03-enrollment-and-progress/
  README.md     <- the contract in prose: wire shapes, tables, gate, definition of done
  backend.md    <- the backend owner's task list
  frontend.md   <- the frontend owner's task list
```

`README.md` is shared and rarely edited. `backend.md` and `frontend.md` are single-owner,
so the two halves tick off tasks without ever touching the same file.

### The workflow, in order

1. **Contract first.** `src/contracts/<feature>.ts` with schemas **and** a `mock`. Register
   in `index.ts`. Commit and push immediately — this unblocks everyone.
2. **Routes next.** `src/app/api/<feature>/route.ts` with `defineRoute(contract)` and **no
   handler**. Push. The endpoint is now live and returns realistic data.
3. **Split.** Frontend builds against `api.<feature>.*` — real HTTP, real types, real
   loading and error states. Backend writes `src/server/<feature>.ts` against the same
   contract.
4. **Land.** Backend adds the handler argument. Frontend changes nothing. Done.

**Steps 1 and 2 are already done for every must-have feature in this repo.** Every contract
and every route stub is committed. That is why all 7 of us start in parallel at minute 20.

### Changing a contract mid-build

You may add an **optional output field** freely. Anything else — renaming a field, changing
a type, making a field required — is a breaking change:

> Post in the team channel: `CONTRACT CHANGE: <feature>.<op> — <what> — <why>`, tag the
> other half's owner, wait for a thumbs-up, then change it in one commit that updates the
> contract, the mock, and the feature's `README.md` together.

## 7. Working in mock mode (this is why nobody is blocked)

The route you need already exists and returns realistic mock data. Just call it:

```tsx
const { courses } = await api.courses.list({ track: 'mandatory' })
```

**You do not need a database or an account to start.** In dev, an endpoint serving mock
data runs as a mock identity instead of returning 401, so a fresh clone gives you working
endpoints immediately. Hard-gated on `NODE_ENV !== 'production'`.

- `?__mock=1` or header `x-mock: 1` forces mock data for one request — use it when a
  backend teammate is mid-refactor on that endpoint.
- `?__mock=error` forces an error response. Build your error state with it.
- `MOCK_DELAY_MS` (default 250) makes loading states visible. Build skeletons.
- Render `<MockBadge source={...} />` on any page whose main data comes from an endpoint,
  so nobody demos mock data believing it's live. **Every MockBadge must be gone from the
  demo path by T+4:15.**
- Browse every endpoint at **`/dev/api`**.
- To work as a mentor before the DB is seeded, sign in as the seeded mentor
  (`mentor@katalyst.test`) rather than hacking the session.

**The AI Coach has its own fallback:** with no `ANTHROPIC_API_KEY`, `src/server/ai-coach.ts`
returns the contract mock instead of throwing. Frontend work on the review UI never blocks
on an API key.

## 9. Domain model — the nouns

Full schema in `plans/katalyst/schema.md`; the code is `src/db/schema/`.

```
user --< enrollment >-- course --< courseSection --< lesson
                          |              |
                          |              +--< assessment --< submission --< aiReview
                          |                                      |
                          +--< challenge                         +-- mentor decision -> xpEvent

user --< xpEvent      user -- streak --< dailyCheckin      user --< userBadge >-- badge
```

- A **course** has `track: 'mandatory' | 'optional'`. Mandatory courses have a `dueAt`;
  optional courses earn **1.5x XP** (`OPTIONAL_TRACK_MULTIPLIER`) — that is how we make
  self-driven learning the attractive choice.
- A **course** may be `certificateEligible` — completing it awards `CERTIFICATE_BONUS` XP
  and a certificate badge.
- A **section** carries `xpAward`. Finishing every lesson in a section completes it and
  fires the award, once, via an idempotency key.
- An **assessment** sits between sections. A **submission** against it gets exactly one
  **aiReview**, then a mentor decision that writes the real `xpEvent`.

## 10. XP rules — the numbers everyone must use

They live in `src/lib/xp.ts`. Import them; never retype a magic number in a component.

| Event | XP | Idempotency key |
|---|---|---|
| Lesson complete | `lesson.xpAward` (default 10) | `lesson:<enrollmentId>:<lessonId>` |
| Section complete | `section.xpAward` (default 50) | `section:<enrollmentId>:<sectionId>` |
| Course complete | `course.xpBonusOnComplete` (default 100) | `course:<enrollmentId>` |
| Certificate course complete | `+200` | `certificate:<enrollmentId>` |
| Assessment — mentor award | mentor's `finalXp`, capped at `assessment.xpAward` | `submission:<submissionId>` |
| Daily check-in | `10` | `checkin:<userId>:<YYYY-MM-DD>` |
| 7-day streak milestone | `50` | `streak:<userId>:<milestone>` |
| Challenge complete | `challenge.xpReward` | `challenge:<challengeId>:<userId>` |
| Badge earned | `badge.xpReward` | `badge:<userId>:<badgeId>` |

**Optional-track multiplier:** every course-derived award above is multiplied by `1.5` and
rounded when `course.track === 'optional'`. Check-in, streak and badge XP are not.

**Levels:** `level = floor(sqrt(totalXp / 100)) + 1` — thresholds 0 · 100 · 400 · 900 ·
1600 · 2500 · 3600. Use `levelFromXp()` and `xpToNextLevel()` from `src/lib/xp.ts`.

## 11. The AI Coach — one file, one model, one schema

Everything lives in `src/server/ai-coach.ts` + `src/lib/ai-prompts.ts`. Owner: **Yash**
(pipeline), **Riya** (prompts and rubric).

```ts
// src/lib/anthropic.ts
import Anthropic from '@anthropic-ai/sdk'
export const anthropic = new Anthropic() // reads ANTHROPIC_API_KEY
export const AI_MODEL = 'claude-opus-5'
```

The review call — structured output, no streaming, so a route handler returns one JSON:

```ts
import { zodOutputFormat } from '@anthropic-ai/sdk/helpers/zod'

const res = await anthropic.messages.parse({
  model: AI_MODEL,
  max_tokens: 16000,
  system: COACH_SYSTEM_PROMPT,          // src/lib/ai-prompts.ts
  messages: [{ role: 'user', content: buildReviewPrompt({ assessment, submission, history }) }],
  output_config: {
    format: zodOutputFormat(AiReviewPayload),  // the SAME zod object the contract exports
    effort: 'medium',                          // bump to 'high' if review quality is thin
  },
})
const review = res.parsed_output      // null if parsing failed — guard, don't assert
```

Rules:

- `export const maxDuration = 60` on every `api/ai-coach/*` route. Reviews take ~10-25 s.
- **No `budget_tokens`.** It is a 400 on `claude-opus-5`. Thinking is adaptive by default.
- **No assistant prefill.** It is a 400 on `claude-opus-5`.
- Check `res.stop_reason === 'refusal'` before reading content.
- The zod schema in the contract IS the schema passed to `zodOutputFormat`. One definition.
- No `ANTHROPIC_API_KEY` -> return `contract.mock(input)` and log a warning. Never throw.
- **The returned `suggestedScore` / `suggestedXp` are advice.** They are stored on
  `ai_reviews` and denormalised onto `submissions.aiScore` / `aiXpSuggested` for list views.
  They never touch `xp_events`.

### The three AI Coach endpoints

| Endpoint | Who | What it does |
|---|---|---|
| `POST /api/ai-coach/preview` | student | Reviews a **draft** before submitting. "Here's what you'd score, here's what to fix." Not persisted. This is the retention hook. |
| `POST /api/ai-coach/review` | student (auto on submit) | Reviews the real submission. Persists an `ai_reviews` row, moves the submission to `ai_reviewed`, puts it in the mentor's queue. |
| `GET /api/ai-coach/brief` | student | Personalised progress update across all their work: strengths, weaknesses, what to do next, which course to pick up. |

## 14. "Where does the backend get deployed?" — it doesn't, separately

The Next.js app **is** the backend. One `git push` produces one Vercel deployment: static
assets and prerendered pages go to the CDN, while `app/api/**/route.ts` and server
components run as Vercel Functions, talking to Neon Postgres over `DATABASE_URL`.

- The API is same-origin (`/api/courses`). The typed client uses **relative URLs** — no
  `NEXT_PUBLIC_API_URL`, no staging/prod URL mismatch.
- **No CORS configuration, ever.** Better Auth cookies are first-party.
- Vercel Functions are stateless and scale to zero — no in-memory cache, no background
  workers, no WebSocket server. The AI Coach runs inline in the request (hence
  `maxDuration = 60`), not in a queue.

**Deploy in the first 20 minutes, with a hello-world page.** Samya owns Vercel env vars and
the production Google callback URL. A first deploy attempted at T+5:00 is how teams lose.
